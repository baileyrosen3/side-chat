Side Chat — product, interaction, implementation, and reliability audit

Audited September 11, 2026. Working tree based on commit `ab24a2c`, including the uncommitted workspace features and the 1.15.2 keypad update. This is an audit and proposed backlog; no application code was changed.

Implementation followed on September 12. This document preserves the original findings; see [the implementation and validation record](audit-fixes-2026-09-12.md) for current behavior and remaining release checks.

The product has a memorable identity and substantial useful functionality. Peek, the screen-edge silhouette, local notes, and continuity with a real agent session are its strongest assets. The execution still feels uneven: basic actions have recovery gaps, the interface devotes considerable space to controls, and some reassuring labels promise more than the underlying behavior delivers. Award-level work here means making ordinary interactions exceptionally dependable and clear.

**The next release should concentrate on three outcomes:** preserve every draft, make actions and their interruption truthful, and make the core workspace feel calm and immediate.

**What was actually checked.** Source review covered the drawer, message rendering, settings, shared controls, Notes/To-dos, capture/search/recovery/export, agent bridge and adapters, permissions, voice/controller lifecycle, computer control, installation, and release documentation. Existing screenshots were inspected, followed by a native fixture using the current components. The fixture used synthetic content and disabled drawer keyboard capture. Reproduction scripts used temporary files and RPC doubles. No real agent task or microphone recording was started.

The workspace changed from 1.15.1 to 1.15.2 during the review. The native and additional reproduction checks used a frozen copy of 1.15.2. [Source fingerprints](audit-evidence-2026-09-11/source-fingerprints.json) identify the reviewed files. The temporary copy of ChatWindow differs only because desktop focus capture was disabled for the visual fixture.

**Prioritized findings.** P1 means address before promoting the app as polished and dependable. P2 means a material everyday usability or correctness gap. P3 means finishing work. “Reproduced” describes a controlled test; “source-confirmed” describes verified implementation behavior without claiming a full desktop reproduction. Product risks and visual judgments are labeled separately.

**1. P1 — Stop can still submit a request during native startup. Reproduced.**

If Stop is requested while `ensure_rpc()` is starting a session, `generate_native()` continues to send the prompt when startup returns. The first cancellation check is inside the subsequent event loop. The RPC double recorded `prompt`, then `abort`, after cancellation had already been set. An actual provider may begin work before that abort is processed.

Evidence: [native_bridge.py](../native_bridge.py), lines 230 and 239; [reproduction log](audit-evidence-2026-09-11/reproductions.log).

Change: check the cancellation generation after startup and branching, before sending; ensure adapter startup is interruptible or visibly cancellable. Acceptance: cancelling during initialization, resume, or fork sends zero new prompts and promptly returns a stopped state.

**2. P1 — New-chat and edit transitions can lose unsent text. Reproduced source logic.**

`startNew()` stops the 500 ms draft timer and clears the composer without flushing the old draft. A newly typed draft followed immediately by New sends only `{action:"new"}`. `edit()` also replaces an existing unsent composer draft with the old message. Cancel then empties the composer instead of restoring that draft. Switching conversations already has an explicit flush; these paths do not. Attachments are also cleared and are not part of durable chat draft persistence.

Evidence: [Main.qml](../Main.qml), lines 158, 165, 185 and 266; [ChatWindow.qml](../ChatWindow.qml), lines 96 and 720. The reproduction executed the extracted production JavaScript functions with a request recorder.

Change: create one draft transition mechanism for new/open/edit/cancel/retry/handoff. Persist text, source, attachments, and separate edit state before changing context. Clear submitted content only after acknowledgment. Acceptance: type → immediately New → return; type → edit an earlier message → cancel; attach → restart. Every original draft must survive intact. Include drafts written while an agent is busy.

**3. P1 — Screen sharing is much broader than the setting's name suggests. Reproduced behavior; product/privacy risk.**

With Peek enabled in Desktop mode, the default `on-request` context setting reacts to ordinary words including “this”, “that”, “here”, and “error”. The existing starter prompt “Explain this project” therefore qualifies to capture the active application and append an image to the agent prompt. A mocked capture confirmed both `hyprctl` and `grim` calls and one attached image. Settings do disclose some trigger words and provider transmission, but the choice is labeled “When I mention my screen”, and the composer offers no pre-send review of the captured context.

Evidence: [peek/context.py](../peek/context.py), line 13; [peek/settings.py](../peek/settings.py), line 17; [PeekSettings.qml](../PeekSettings.qml), lines 198 and 202; [native_bridge.py](../native_bridge.py), line 212.

Change: use explicit screen intent, or a visible per-request context attachment that can be inspected/removed. Show which application will be shared before dispatch. Acceptance: “Explain this project” sends no screenshot by default; an explicit screen request makes the selected context visible and removable. This is an expectation mismatch, not a demonstrated permission-system bypass.

**4. P1 — Mature conversations cause substantial synchronous UI work. Reproduced.**

The thread is a Flickable containing a Column/Repeater, so every message gets instantiated. Each message also eagerly constructs its blocks and tool contents. Creating 1,000 modest synthetic messages took **2,380 ms** from assignment to the next Qt callback in the native fixture. That is a single local sample, not a p95 benchmark, but it establishes an expensive path. Production also creates a ChatWindow per monitor, multiplying the potential work.

Evidence: [ChatWindow.qml](../ChatWindow.qml), lines 627 and 634; [MessageCard.qml](../MessageCard.qml), lines 18 and 215; [Main.qml](../Main.qml), line 334; [native log](audit-evidence-2026-09-11/preview-current.log).

Change: use a virtualized thread, stable message IDs, lazy tool/detail creation, and incremental streaming updates. Preserve text selection and scroll position while doing so. Acceptance: 1,000-message history remains responsive; old offscreen messages do not all have live delegates; opening another conversation does not stall shell interaction.

**5. P1 — Physical takeover and emergency-stop availability are overstated. Source-confirmed.**

The input watcher stops on mouse movement or typing only while `self.active` is true. That flag covers individual injection operations and becomes false between them. Moving the mouse between agent actions therefore does not reliably cancel the remaining desktop turn. Separately, `capabilities` reports `takeover: true` even when evdev is unavailable or no input device can be opened. Settings and the companion hint advertise Ctrl+Alt+Esc without checking that prerequisite.

Evidence: [peek/control.py](../peek/control.py), lines 99, 126, 259, 271 and 280; [PeekSettings.qml](../PeekSettings.qml), line 207; [CompanionSurface.qml](../CompanionSurface.qml), Stop control.

Change: track actual input-monitor availability, arm takeover for the desktop-control turn, and ignore the agent's own synthetic input explicitly. Expose the real stop capability in UI. Acceptance: a real user movement between two planned actions prevents the second; missing permissions produce an unavailable status rather than a false capability. Physical-device validation remains required.

**6. P1 — Damaged recovery data can produce partial saves and broader outages. Reproduced and source-confirmed.**

A new note's Markdown is committed before `save()` reads and removes its entry from `drafts.json`. With invalid recovery JSON, the operation raises `JSONDecodeError` after one Markdown file is already committed. A retry has no stable identity and can produce a duplicate. Separately, malformed chat/settings JSON is decoded without quarantine during Bridge initialization, before the main error handler is active; that can make the whole backend repeatedly fail to start.

Evidence: [thoughts.py](../thoughts.py), lines 216 and 219; [backend.py](../backend.py), lines 263, 274 and 751; [reproduction log](audit-evidence-2026-09-11/reproductions.log).

Change: isolate corrupt records, preserve their bytes for recovery, validate recovery state before committing, and give saves idempotent operation IDs. Acceptance: damaged drafts do not prevent opening other notes or chat; an ambiguous save retry produces exactly one item; the UI distinguishes “saved, recovery cleanup failed” from “not saved”.

**7. P2 — Fast submission can skip a supported reminder. Reproduced in QML.**

The reminder parser accepts “at noon” and “at midnight”, but the QML `dateCandidate` expression only recognizes numeric time after “at”. Immediately saving “Call Alex at noon” sends `due: 0` before the preview timer returns. Waiting for the preview changes the result, so correctness depends on typing speed.

Evidence: [ThoughtsModel.qml](../ThoughtsModel.qml), lines 31 and 127; [reminders.py](../reminders.py), `CLOCK`; [QML reproduction log](audit-evidence-2026-09-11/qml-audit.log).

Change: derive reminder readiness from one parser contract, with a parse-generation requirement for all candidate inputs. Acceptance: immediate Enter and delayed Enter have the same result for every documented expression, including noon, midnight, invalid dates and DST transitions.

**8. P2 — Long attachment names overflow and hide the removal affordance. Reproduced visually.**

An attachment button measured **803 logical pixels inside a 337-pixel drawer**. Its close glyph sits beyond the visible boundary. `Layout.maximumWidth` is attached to a child of Flow, which does not enforce Qt Quick Layout sizing.

Evidence: [ChatWindow.qml](../ChatWindow.qml), line 745; [geometry](audit-evidence-2026-09-11/attachment-geometry.json); [capture](audit-evidence-2026-09-11/attachment.png).

Change: bound the actual width to the available row width, elide the filename, and keep a separate removal target visible. Acceptance: eight long filenames, Unicode, spaces and narrow drawers produce no horizontal overflow; each attachment remains removable by mouse and keyboard.

**9. P2 — Stopped tools are summarized as completed. Reproduced in QML.**

ToolActivity counts only running and error states. When a tool has `status:"stopped"`, its summary becomes “1 action completed”. Native cancellation explicitly produces this stopped state. The detailed task verifier already has a more careful model; the thread summary undermines it.

Evidence: [ToolActivity.qml](../ToolActivity.qml), lines 13 and 23; [native_bridge.py](../native_bridge.py), line 280; [QML reproduction log](audit-evidence-2026-09-11/qml-audit.log).

Change: summarize complete/stopped/failed/unknown separately and reserve verified language for actual evidence. Acceptance: mixed tool outcomes remain truthful in collapsed and expanded views, after cancellation and after restart.

**10. P2 — The documented visual preview is broken against the current component contract. Reproduced natively.**

DesignPreview's chat double lacks workspace, thoughts, focusWorkspace and preferencesRequested, which ChatWindow now expects. The baseline emitted repeated undefined-property and missing-function warnings. To inspect current native layouts, this audit added those contracts only to a temporary fixture copy.

Evidence: [DesignPreview.qml](../DesignPreview.qml), chat fixture; [baseline log](audit-evidence-2026-09-11/preview-baseline.log).

Change: maintain a shared fixture model, deterministic scenarios and a warning-as-failure smoke check for the documented preview. Acceptance: a clean checkout can preview every shipped page without production data or QML warnings.

**11. P2 — Erasing a new note draft can resurrect the erased text. Reproduced in QML.**

After a draft is stashed, clearing the editor and stashing again returns early because the body is empty and there is no note ID. The previous nonempty draft remains in the model and recovery file. A later recovery can bring back text the user intentionally removed.

Evidence: [ThoughtsModel.qml](../ThoughtsModel.qml), line 120; [QML reproduction log](audit-evidence-2026-09-11/qml-audit.log).

Change: persist empty-draft deletion/tombstones and invalidate stale in-flight acknowledgments. Acceptance: type → wait for draft save → select all/delete → change tabs/restart never restores the old text.

**12. P2 — Important navigation destinations are missing. Source-confirmed.**

Rendered message links only open HTTP(S), so ordinary local file links from coding agents do nothing. Unified search matches full conversation bodies but returns only the conversation ID; activation opens the conversation without a message anchor or match highlight. A result deep in a long conversation is therefore difficult to locate after opening it.

Evidence: [MessageCard.qml](../MessageCard.qml), line 287; [workspace.py](../workspace.py), line 115; [WorkspaceModel.qml](../WorkspaceModel.qml), line 72.

Change: support validated local paths through the configured editor and preserve message IDs/match offsets in search results. Acceptance: file links open the intended location; selecting a body match lands on and highlights that message. Unsupported destinations must give feedback.

**13. P2 — Settings lose the user's place and mix several save contracts. Source-confirmed behavior; UX judgment.**

Preferences opened from Notes returns to Chat. Permissions opened from Preferences also returns to Chat. Conversation options, global agent defaults, desktop appearance, recovery and voice settings share the same route, while some changes apply immediately and others require Save or Apply. The explanatory copy helps, but the navigation still makes users reason about implementation boundaries. The global settings button is disabled during an agent reply, including access to unrelated data/recovery preferences.

Evidence: [ChatWindow.qml](../ChatWindow.qml), lines 60, 80, 424, 1157, 1209 and 1416; [backend.py](../backend.py), line 693; [PeekSettings.qml](../PeekSettings.qml), line 225.

Change: preserve the caller route, separate “This conversation” from “App preferences”, and standardize save behavior within each surface. Keep unrelated preferences usable during work. Acceptance: Notes → Preferences → Permissions → Back → Back returns to the original note/draft, with no unintended defaults changed.

**14. P2 — Interaction targets and text scaling are inconsistent. Source-confirmed; full assistive-technology review outstanding.**

Shared controls have accessible names and visible focus treatment, which is a good start. Message actions explicitly shrink to 20 scaled pixels; several tool controls use 22. Thoughts uses fixed `Style.space(13/14)` text while ChatStyle follows `Style.font.body`. Increasing the desktop font therefore affects the surfaces differently. Dense controls and hidden hover actions need testing for users who do not use a precise mouse.

Evidence: [MessageCard.qml](../MessageCard.qml), lines 128, 138 and 261; [ToolActivity.qml](../ToolActivity.qml), line 50; [ThoughtRow.qml](../ThoughtRow.qml), line 75; [ThoughtsView.qml](../ThoughtsView.qml), line 87; [ChatStyle.qml](../ChatStyle.qml), line 18.

Change: use shared typography tokens and a comfortable minimum hit area, while keeping compact glyphs. Validate Tab order, automatic scrolling to focused controls, accessible state announcements, and larger fonts. W3C's 24×24 CSS-pixel target-size criterion is a useful reference with spacing exceptions; it is not automatically a native-QML conformance test. [W3C target guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum). Qt documents the metadata required for custom accessible controls. [Qt Quick accessibility](https://doc.qt.io/qt-6/accessible-qtquick.html).

Acceptance: complete capture, save, find, edit, delete/undo, approval and Stop by keyboard; check with Orca; inspect 100%, 150% and 200% scaling and an enlarged desktop font.

**15. P2 — Search and history need a scaling strategy. Measured fixture behavior and source review.**

Search reads every chat JSON record and joins every message on each query. With 2,000 notes and 1,000 conversations in a 43 MB chat database, this machine measured 282 ms cold and about 185–190 ms warm, before UI debounce/rendering. That is already noticeable for an instant-search surface. Search, capture, restore and export share one worker; a long export can delay capture and search. The stale-query guard drops superseded results but does not cancel a running scan.

Evidence: [workspace.py](../workspace.py), lines 56, 115 and 146; [reproduction log](audit-evidence-2026-09-11/reproductions.log).

Change: use a maintained local search index, cancellable jobs and separate interactive work from long exports. Paginate results and include their exact destination. Acceptance: a representative mature workspace meets an agreed search latency budget and remains searchable while a backup runs.

**16. P3 — Reduced motion and monitor recovery have unfinished edges. Source-confirmed risks.**

The main drawer and companion honor reduced motion, but ActionButton and MessageCard still hard-code 130–140 ms opacity animations. Display removal repairs `companionScreen` only, leaving an open drawer's `openScreen` potentially pointing at a disconnected display. The user can reopen it, but automatic recovery is incomplete.

Evidence: [ActionButton.qml](../ActionButton.qml), line 69; [MessageCard.qml](../MessageCard.qml), lines 108 and 172; [Main.qml](../Main.qml), line 347.

Change: centralize motion preferences and route all visible surfaces to a valid monitor after topology changes. Acceptance: reduced motion suppresses nonessential effects everywhere; unplugging the active display preserves and moves the open draft. Hot-plug behavior was not physically exercised in this audit.

**Visual and product direction — design recommendations**

The current [Chat capture](audit-evidence-2026-09-11/current-empty.png) and [Notes capture](audit-evidence-2026-09-11/current-notes.png) show both the identity and the opportunity. The shaped border and Peek are recognizable. The dense header, duplicate status markers, navigation strip, page toolbar and large empty composer compete for attention. Notes takes much more vertical space than a short chat even with one small item. Square shadowed action buttons coexist with rounded tabs, fields and note cards without a clear hierarchy.

| Area | Recommended direction | Concrete result |
| --- | --- | --- |
| Product promise | “Capture a thought, turn it into useful work, keep the result.” | A coherent workflow connecting the existing features |
| Drawer composition | Keep one quiet identity/status row, shared navigation, content, and the current primary action | More space for the thing the user came to read or do |
| Visual system | Define semantic roles for surfaces, borders, radii, type sizes and action emphasis | Existing Omarchy themes feel intentionally adapted across every page |
| Primary controls | Clearly distinguish Save note, Add task, Send request, Stop and Redirect | The same arrow does not need to carry several meanings; Stop remains visible while redirecting |
| Content reading | Establish a comfortable reading measure; preserve code indentation and allow horizontal code scrolling | Long replies and code remain useful in both compact and expanded views |
| Peek | Use expression to acknowledge real events: heard, waiting, interrupted, verified | Personality reinforces trustworthy status |
| Progress | Use one shared result model for conversation tools and the companion | “Done”, “stopped”, “needs review”, and “verified” agree everywhere |
| Context | Visible chips for source note, files, screen, working folder, and provider where relevant | The user can understand the request before sending |
| Notes/tasks | Clear editing identity, due-state cues, recoverable drafts, optional preview/read mode | Saving and reopening feel as polished as initial capture |
| Search | Exact destinations, match highlighting, optional type filtering, useful empty state | Finding content actually takes the user to it |

Keep the desktop's font and theme integration. Tune hierarchy through spacing, weight, content width and semantic tokens before introducing another brand font or decorative effect. Peek already supplies enough character.

Apple's feedback guidance supports integrating status with the relevant interaction and matching interruption to importance. Apply that principle to saves, errors, approvals and verified actions rather than adding more disconnected notifications. [Apple feedback guidance](https://developer.apple.com/design/human-interface-guidelines/feedback).

**Make the first minute self-explanatory.** The app currently relies heavily on a long README and terminal setup. Offer a small readiness view: chosen agent available, voice optional, microphone off, desktop control available/unavailable. Let someone save a first note immediately, then invite a short microphone test and explain whether stopping recording saves a draft or sends a request. Derive visible shortcut hints from one binding definition and provide an in-app map; this should work for people without the developer's keypad.

**Make the signature demonstration a real workflow.** Select text → capture with its source → keep it as a note → discuss it in the existing conversation → review the requested action → inspect the result → retain the useful answer or create a reminder. Every step already has much of its foundation. Connect the steps with clear destinations and reversible transitions, and let Peek acknowledge them subtly. This demonstrates the product's identity more convincingly than an animation showcase.

**Privacy and data lifecycle.** Positive foundations include local speech, microphone off by default, reuse of existing CLI credentials, explicit note-to-chat sharing, revision-checked writes, private state directories, and conflict-aware tracked config undo. Preserve those. Add an inspectable “what this request includes” view, storage/retention controls and an understandable backup/restore flow. Recently deleted currently retains data indefinitely, and chat deletion leaves attachment snapshots and external native sessions; the README explains this, but users need the distinction in the app. A workspace backup is not a complete backup of the CLI agents. Add a restore rehearsal to release checks, including relocation and attachment paths. Do not present tracked config undo as undo for arbitrary agent actions.

**Engineering and release work.** Keep the native QML/Python stack. Split the 1,500-line ChatWindow by responsibility so conversation UI, app settings and navigation can be tested without recreating the entire shell. Add a typed command/event contract with request IDs, acknowledgment, cancellation generations and explicit recovery outcomes. Avoid strings and loosely coupled booleans being the only definition of a task's state. Preserve provider-specific permission semantics and test startup/resume/branch/approval/handoff contracts for each supported adapter. The current tests are valuable, but substring checks and small isolated fixtures do not establish complete user-flow correctness.

Automate the release gates already described in the project: clean staging validation, required-runtime tests, warning-free preview, representative native fixtures and install/update smoke checks. Add dependency compatibility information and a diagnostic export that omits conversation content and credentials. Installation already has useful pinning/checksum and private-runtime work; this audit did not perform a clean machine installation or a new supply-chain vulnerability scan.

**Suggested implementation sequence and acceptance gates**

| Order | Scope | Done means |
| --- | --- | --- |
| 1 — Trust | Findings 1, 2, 3, 5, 6 and 9 | Stop never submits late; drafts survive transitions; sharing is explicit; reported capabilities/results are accurate; recovery failures do not duplicate work |
| 2 — Core interaction | Findings 7, 8, 11, 12 and 13 | Reminder timing is deterministic; attachments fit; erased drafts stay erased; links/search land correctly; Back preserves context |
| 3 — Performance and accessibility | Findings 4, 14, 15 and 16 | Large histories remain usable; keyboard/Orca flows work; scaling/motion/monitor changes preserve access |
| 4 — Product finish | Shared visual tokens, calmer composition, readiness flow, the signature workflow | A new user completes the core workflow without reading setup documentation or needing the developer's keyboard |
| Throughout | Finding 10 and release automation | The documented preview and release checks exercise the current component contract |

Proposed performance targets, to agree and measure rather than advertise as achieved: visible click/key acknowledgment within 100 ms; warm drawer readiness within 150 ms; indexed search within 100 ms at the reference library size; no long-history operation that blocks the GUI for hundreds of milliseconds. Measure p50/p95 over repeated runs and include idle CPU/memory, multi-monitor composition, ASR/TTS warmup and end-of-speech latency.

**What still requires real-world validation.** Live microphone accuracy and echo/barge-in quality, actual provider login/streaming/billing, physical takeover and emergency Stop, desktop hot-plug/suspend, Orca, IME/non-English input, and fresh install/update/remove were not exercised end to end. The QML fixture disabled drawer focus capture to protect ongoing desktop input, so it does not validate compositor focus behavior. A single synthetic load timing cannot establish production p95 responsiveness. Accessibility guidance is used as a design benchmark, not a formal compliance claim.

The highest-value next step is a focused trust-and-coherence release. Side Chat already has enough capabilities to deliver a distinctive experience; its strongest improvement opportunity is the quality of the transitions between them.
